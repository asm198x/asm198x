The acquisition at `/private/tmp/asm198x-ecosystem-batch-sources` contains the eight manifest-pinned, clean source trees. No upstream Makefile or script was executed during acquisition/review. Licence paths were inspected; retained binary-byte facts carry the complete captured notice, its digest, the SPDX expression and original path.

- ACME: the three existing native argv invocations emit their complete PRG files. Asm198x uses the same root source and CPU, with PRG framing.
- NES-ca65-example: pinned `compile_example.bat` invokes ca65, then ld65 with `example.cfg`. The Python FCEUX symbol helper is outside the final ROM boundary. The reference plan keeps native object and final ROM stages; Asm198x uses its fused assembler/linker with the unchanged project configuration. The tracked sample ROM is removed only from the fresh execution copies before building.
- cc65 opcode targets: pinned `test/asm/opcodes/Makefile` uses ca65 then ld65 under the `none` layout and compares final raw bytes with the supplied `.ref`. The three pinned sources contain only CODE instructions and no runtime imports; the adapter is separately hashed and copied without editing source. Final `.bin` files, not `.o` files, are the comparison boundary.
- Unbricked: pinned `unbricked/bricks/build.sh` names rgbasm, rgblink and `rgbfix -v -p 0xFF`. Those three argv stages are represented explicitly. Asm198x's `--gb-rom` produces the same finalised ROM boundary. The upstream shell script is read, not executed.

Asm198x uses the unchanged root source and source-requested NEX output. A parser rejection remains a rejection; a raw assembler image is never compared with a NEX container.
- HelloAmi: the existing native hunk-executable invocation is retained, without its optional symbol table. Asm198x's vasm frontend emits the hunk-executable boundary. Disk-image and emulator helpers are not part of this executable comparison.

Each execution captures the native executable hashes and exact reviewed version lines. Local RGBDS is 1.0.4 versus the arbiter image's 1.0.3; local vasm is 2.0b versus the image's 2.0f. Both identities are explicit in the plan, and their controls are independent observations, not interchangeable binaries. A mismatch outside the reviewed list is infrastructure unavailable, never an Asm198x incompatibility verdict.

The first complete audit also checked the adapters themselves. CLI CPU selectors do not share every spelling with native tools or manifest CPU metadata (`6510` and `4502` were rejected before assembly). The corrected Asm commands use the dialect's default/unchanged lexical CPU directives. These were audit-plan errors, not compatibility findings. The complete Game Boy source tree is about 128 MB, including 25–33 MB documentation GIFs; source hashing/copying uses the declared 512 MiB tree bound, independently of the 16 MiB generated-artifact bound. Keeping that complete tree avoids inventing an extracted source target.

A focused framing control established that HelloAmi's apparent mismatch was an audit-plan error: the initial Asm command omitted `--exe` and produced raw code. With the full acquired source context and that flag, both tools emit the same 244-byte hunk image, SHA-256 `826d98fbcae710038965fb94e5366acf8bbf4af1ab11a61c3e2aad5945c32dab`. The corrected plan is guarded against selecting raw output for a native `-Fhunkexe` comparison. No HelloAmi compatibility issue follows from the rejected initial comparison.

The accepted 4510 native adapter emits 564 bytes, exactly matching the pinned upstream `4510-opcodes.ref`. The remaining Asm boundary is the real unfilled used-extent layout restriction, not a changed native byte boundary.
